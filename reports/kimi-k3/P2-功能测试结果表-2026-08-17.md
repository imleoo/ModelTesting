## 四、关键发现（均可通过 `run-2026-08-17.json` 对应 `case_attempts` 追溯完整请求/响应体）

1. **`enable_thinking:false` / `thinking:{"type":"disabled"}` 均无法真正关闭思考**。请求返回 HTTP 200，但响应仍然携带非空 `reasoning_content`（如 `enable_thinking:false` 时仍返回 63 个 `reasoning_tokens`，对照同一用例 `on` 变体的 148 个，`off` 明显没有归零）。两次请求（开/关）本身都成功送达并拿到合法响应，只是关闭开关未生效——这是模型/网关侧的真实行为，不是测试台的请求构造问题。

2. **`chat_template_kwargs.*` 两种方式被网关直接拒绝**，返回 `HTTP 400 {"error":{"message":"request features could not be classified for routing"}}`。这说明该网关当前的请求路由/分类层不识别 `chat_template_kwargs` 这个参数名，与 SCHEMA.md 里标注的"待联调验证"假设不同——不是格式错误，是该参数路径本身未被支持。

3. **`reasoning_effort` 的 low 档 3 次采样结果分散（398 / 1947 / 1081 个 `reasoning_tokens`），未形成严格多数**，判定聚合失败。9 次实际请求全部成功拿到有效响应（`attempts=9 passed=9`），只是同一档位下的输出长度波动很大，用众数聚合规则判定为"无法可靠代表该档位"。附带观察：本次单次采样里 low 档（1947）个别样本的 `reasoning_tokens` 反而高于 high 档（616/652/225），说明 `reasoning_effort` 参数对推理量的影响本身不稳定，不是简单的单调递增关系；样本量小（每档 3 次）不足以下更强结论，需要更大样本量才能判断这是偶发方差还是参数确实弱相关。

## 五、已知限制（非本次测试范围内可解决）

- **`image_url` / `video_url` 未测试**：需要一个 tokenpanel/上游可达的公网素材托管地址（`TESTBED_PUBLIC_BASE_URL`），P0 阶段已标注为部署阶段待确认项（见 `suites/kimi-k3/materials/manifest.json` 的 `hosting` 字段），本次本地开发环境无法提供，留待部署阶段补测。
- **`reasoning_effort` 众数聚合样本量偏小**：当前 `repeat_attempts=3`，面对高方差指标容易出现"3 次互不相同、无多数"的情况；是否需要提高采样次数或改用其他聚合方式（如判断区间重叠而非严格众数）是后续可以讨论的设计取舍，不在本次实现范围内调整。

## 六、本次真实测试过程中修复的实现缺陷

真实联调过程中发现并修复了两处测试台自身的实现问题（详见对应 git commit）：

1. `openai_schema_valid` 曾要求非流式 `message.content` 键必须存在（可为 null），但真实 kimi-k3 网关返回 `tool_calls` 时会直接省略 `content` 字段而非显式置 null——这是合法的 OpenAI 兼容行为，此前的校验过严，已放宽为"出现时才校验类型"。
2. `structured.json_schema` 用例原提示词询问"北京当前天气"，模型如实以 `null` 回答无法确定的实时温度（在 `reasoning_content` 里明确说明了这个理由），导致结构化输出的类型校验失败——这是测试题设计缺陷（问了模型无法确定性回答的问题），已改为要求模型填入测试固定值的虚构示例，与真实天气数据脱钩。
