## 四、关键发现（均可通过 `run-2026-08-18-official.json` 对应 `case_attempts` 追溯完整请求/响应体）

1. **`protocol.usage_stream` 两段式尝试均未拿到 usage 字段**：先不带 `stream_options.include_usage` 发起流式请求（末包无 `usage`），追加该参数重试一次仍未拿到（0/2 通过）。与此前对 tokenpanel/新中转的测试结果一致，官方 API 在流式场景下不回传 usage，即使显式请求 `stream_options.include_usage` 也不生效。

2. **`video_base64` 在官方 API 上通过，与 tokenpanel/新中转的表现不一致**：此前两个网关（tokenpanel 08-17、新中转 we2ai 08-18）均以 HTTP 400 拒绝套件冻结的 video content part 假设 schema（`{type:"video_url", video_url:{url:"data:video/mp4;base64,..."}}`，见 `SCHEMA.md` 未决项 1），本次官方 API 正确接受并返回预期答案。说明该 schema 假设本身是官方支持的格式，此前两个网关的 400 拒绝是网关/中转层自身的兼容性限制，不是套件用例构造有误。

3. **`tool.choice_allowed_tools` 零次工具调用**：请求送达且返回 HTTP 200，但响应里没有任何 `tool_calls`（0 次调用）。按 04 节从严解释（`tool_call_subset` 断言要求 ≥1 次调用，PDF 原文只要求"在给定子集内选择"未明确要求至少调用一次），零次调用不视为通过。与新中转 we2ai（同样 FAIL，但表现为 HTTP 400 拒绝 `tool_choice` 字段）不同，官方 API 是接受了这个请求格式、只是模型选择不调用工具——两者都是 FAIL 但故障模式完全不同：新中转是协议层拒绝，官方 API 是模型行为层面的"不配合"。

4. **思考开关 4 种方式中，仅 `thinking.type` 真正生效**：`enable_thinking:false`（顶层参数）、`chat_template_kwargs.enable_thinking:false`、`chat_template_kwargs.thinking:false` 三种方式请求均成功送达并拿到合法响应，但关闭开关未生效——响应仍携带非空 `reasoning_content`，与此前两个网关的表现一致。**唯一的例外是 `thinking:{"type":"disabled"}` 这种方式**：开启（`thinking:{"type":"enabled"}`）时正确返回 `reasoning_content`，关闭时正确不返回，两次请求均通过。这是三次真实测试（tokenpanel/新中转/官方 API）里第一次观察到有任意一种思考开关方式真正生效，指向该模型/接口实际只认可 `thinking.type` 这一种控制方式，其余三种参数被静默忽略。

5. **`reasoning_effort` 三档的 `reasoning_tokens` 实测**（每档 3 次采样）：low=485/630/691、high=417/509/524、max=4804/1129/1628。9 次请求全部成功。low 档三次采样彼此接近（485-691 区间），本应能形成多数/中位数意义上的合理聚合，但当前引擎的"多数结果"判定要求同档采样值**完全相等**才算形成多数，三个互不相同的整数值（485≠630≠691）严格意义上没有任何一个值出现两次，判定失败。这印证了此前 Fable 5 终验指出的规格层问题：04 节"取多数结果"的字面实现（`majority()`，`internal/engine/engine.go:612`）在非确定性模型下对任何有轻微波动的采样都是结构性易败的，即便三次采样彼此已经很接近、方向也符合"low < high"的预期（除 max 档波动较大外）。

6. **`input_validation.duplicate_content_parts` 未被拒绝**：content 数组里两个完全相同的 text part（`[{"type":"text","text":"重复内容测试"},{"type":"text","text":"重复内容测试"}]`）被官方 API 当作合法输入接受并正常处理返回 HTTP 200，不是本次新增 5 项用例里描述的"透传后端触发 500"场景，而是网关/模型层面直接容忍了这种输入、没有报错也没有触发异常——语义上确实是一种校验缺失（重复 part 理论上应该被规范化或拒绝），但没有造成 500 这类更严重的问题。这是当前 `rejects_invalid_request` 断言类型判定规则的一个边界情况：200（正常处理）判 FAIL 的理由是"网关完全没做校验"，但这里更准确的描述是"网关选择宽松接受"而不是"透传崩溃"，严重程度不同但当前判定逻辑没有区分。

## 五、已知限制（非本次测试范围内可解决）

- `image_url` / `video_url` 未测试：无公网可达素材托管地址，留待部署阶段补测。
- `reasoning_effort` 众数聚合规则的结构性问题（见「四、关键发现」5）：建议下一版设计方案把"取多数结果"改为中位数比较或分桶多数，否则该用例对多个真实供应商/接入方式都会是结构性 FAIL。

## 六、三方对比结论（tokenpanel vs 新中转 we2ai vs 官方 API，均为 2026-08-17/18 测试）

| 用例 | tokenpanel（08-17） | 新中转 we2ai（08-18） | 官方 API（08-18） |
|---|---|---|---|
| 22 项基础用例通过数 | 15/19 | 13/19 | 14/19 |
| protocol.usage_stream | ✅ PASS | ✅ PASS | ❌ FAIL（两段式均无 usage） |
| multimodal.video_base64 | ✅ PASS | ❌ FAIL（400） | ✅ PASS |
| tool.choice_allowed_tools | ✅ PASS | ❌ FAIL（400，协议层拒绝） | ❌ FAIL（0 次调用，模型层不配合） |
| thinking 4 种关闭开关 | 4/4 FAIL | 4/4 FAIL | **1/4 通过**（`thinking.type` 生效） |
| reasoning_effort.scaling | ❌ FAIL | ❌ FAIL | ❌ FAIL（现象一致，均为聚合规则问题） |

三方表现均不完全一致，且没有一方是"更权威"的基准——tokenpanel/新中转是中转层，官方 API 是直连但同样暴露了 `usage_stream` 缺失等问题。`thinking.type` 只在官方 API 上生效这一发现最值得跟进：如果中转层能正确透传该参数，思考开关本应有一种可用方式，而不是全部 4 种在中转场景下都不生效。
