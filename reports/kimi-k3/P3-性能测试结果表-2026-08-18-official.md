## 结果解读

1. **TTFT/缓存命中率均达标，无任何失败样本**：TTFT P50=2.614s，远优于 15s 基线；91 个请求全部成功（0 失败），优于此前 tokenpanel 网关（2 次超时失败）。缓存命中率 avg=0.978（97.8%），`usage.prompt_tokens_details.cached_tokens` 在官方 API 下同样是真实可观测字段。

2. **TPOT P50=0.009ms 存在解读陷阱，不能直接当作"极快"**：44 个观测样本呈明显双峰分布——36 个样本 TPOT 集中在 0.002~0.024ms 区间（对应 output_tokens 较少、且 `TTFTSeconds == LatencySeconds` 的请求，即首个非空内容分片到达后几乎在同一时刻就完成了整个响应，说明官方 API 对这类短输出实际上是"一次性突发返回"，不是真正的逐 token 增量流式），另有 8 个样本落在 3.8~12.3ms 的正常区间（对应输出更长、能观察到真实分片间隔的请求）。P50 落在低峰区间，数值本身符合 TPOT 的标准定义（`(DoneAt - FirstContentAt) / (output_tokens - 1)`），判定 OK 没有计算错误，但把 0.009ms 读成"官方 API TPOT 极优"是误导——真实含义是"短输出场景下官方 API 的流式颗粒度粗到测不出真正的逐 token 间隔"，这是被测 API 自身的流式实现特征，不是压测引擎的缺陷。建议后续报告口径里，TPOT 双峰分布本身也是一项值得留痕的观察，而不只是看 P50 数字。

3. **throughput_req_s 判 FAIL 是采样规模问题，不是被测系统缺陷**：3 个会话在 756.2s 内合计完成 91 个请求，平均吞吐 0.120 req/s，低于 0.6 req/s 基线。这与此前 tokenpanel（0.071 req/s）、新中转 we2ai（0.123 req/s）一样，是 3 会话冒烟规模下到达事件过早完成、无法形成稳态吞吐所致，不代表 kimi-k3/官方 API 的真实吞吐能力。要让吞吐指标有意义，需一次达到目标并发规模的正式压测。

4. **Latency/ITL 按设计方案首版口径仅记录、置 MANUAL_REVIEW**：ITL 的双峰分布（P50=0.021ms vs P95=236.201ms）与 TPOT 观察到的同一现象呼应——短输出场景下 SSE 分片几乎同时到达，长输出场景下才呈现真实的分片间隔。

## 已知限制

- 本次仅覆盖 3 会话小规模冒烟，**未验证目标并发规模下的真实吞吐**；正式验收前建议按 6.1 节固化参数用更大 `-total-sessions` 跑一次完整压测。
- Latency/ITL 首版仅记录，需等历史对比能力上线后才有判定依据。
- TPOT/ITL 的双峰分布现象（见「结果解读」2）目前只在本报告文字说明里记录，压测引擎本身未对"是否存在真正的逐 token 流式颗粒度"做专门的可观测性判定或标注，如果后续需要机器可读的方式区分这两种模式，需要在设计方案层面补充口径。
